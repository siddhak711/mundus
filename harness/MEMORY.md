# Memory and context design: office-to-apartment conversion agent

Draft, 2026-11-15. Sources are listed at the end. Where this file disagrees with what is built, the code wins; update this file.

As built (mundus_harness/conversion/): `/memories/` is a folder on disk (harness/data/conversion_memory/, or
CONVERSION_MEMORY_DIR), shared by every run; `/skills/` is harness/skills_conversion/ (read-only). Write rules are
deepagents FilesystemPermission per agent: allow `/memories/<own>/**` (orchestrator also INDEX.md), then deny
`/memories/**` and `/skills/**`; a test proves a cross-folder write is refused. Reference data is
data/conversion/<scan>/ (floorprep output), read only through tools. Drafts live in data/conversion/<scan>/drafts/
instead of `/work/`. There is no web search, so the compliance rules are seeded in the skill, all unconfirmed.

## 1. What memory is for

Memory holds what an agent cannot re-read from the environment and will need again. Anthropic's memory research puts
it as: a written rule is a prediction that the pattern will matter again. So:

- Do not store what a tool can recompute: floor geometry, CoStar numbers, distances. Those live in `/world/` and are
  read fresh.
- Do store what took effort or judgment to learn: a city's conversion rules and their sources, layout strategies that
  passed or failed and why, data quirks (for example "this scan has no walls in the API, use the mesh cut").

## 2. The file system (four layers)

Ordered from the always-loaded layer down to the raw record, as in Anthropic's memory hierarchy.

| Layer | Path | Contents | Written by | Lifetime |
|---|---|---|---|---|
| Injected context | `/memories/INDEX.md` | At most 60 lines: what each memory folder holds, the current priorities, the rules for using memory. Loaded into every agent's prompt | Orchestrator only | Permanent |
| Memory notes | `/memories/<owner>/...` | Rules, lessons, quirks, each with status and evidence | The owning agent only (section 3) | Permanent |
| Reference data | `/world/floors/<id>/` | `floor.json`, `structure.json`, `costar.md` | Ingest code only. Read-only for agents | Permanent, regenerated by ingest |
| Working files | `/work/<run_id>/` | `draft_vN.json`, `compliance_report.md`, `cost.md`, `layout.json` | Any agent, in its own file | One run |
| Transcript | LangSmith traces | Every model and tool call | The harness | Permanent |

Skills (`/skills/layout/`, `/skills/compliance-la/`, `/skills/cost/`) are our instructions, not memory. Agents read them
and never write them.

## 3. Who writes memory: every agent, each in its own folder

Every subagent may write memory, because each learns things the others cannot: the compliance agent learns rules, the
layout agent learns which shapes fail, the cost agent learns rent quirks. The constraint is **ownership, not
permission**. In Anthropic's test, agents sharing one table erased each other's lines and only 41 of 57 facts survived.
Giving each page one owner kept all 57.

```
/memories/
  INDEX.md                  orchestrator
  compliance/la.md          compliance subagent: rules, each with source URL and date
  layout/lessons.md         layout subagent: strategies that passed or failed, and why
  cost/assumptions.md       cost subagent: rent sources, cost-per-sq-ft assumptions
  data/quirks.md            orchestrator: data problems found (missing walls, unscanned stairs)
```

An agent may read every folder but write only its own. Enforce this in the backend with path permissions per
subagent; a prompt instruction alone is not enough.

## 4. When memory is written

| Moment | Who | What |
|---|---|---|
| Start of every run | Every agent | Read `INDEX.md`, then only the files it points to for this task. Do not load everything |
| After researching a rule | Compliance | Add it to `compliance/la.md` with source, date and `status: unconfirmed` |
| When a rule is confirmed by a second source or by the orchestrator | Compliance | Change it to `status: confirmed` |
| After a draft passes or fails compliance | Layout | One line in `layout/lessons.md`: what was tried, the result, the evidence (report path) |
| When something is clearly worth remembering, or the user says "remember" | Any agent, own folder | One entry |
| End of run | Orchestrator | Update `INDEX.md` if folders or priorities changed; append to `data/quirks.md` |

Do not write on a fixed rule such as "record only failures". Anthropic measured that rule lowering the benefit of
memory. Do not log everything either: one model wrote 413 files and spent its steps curating them.

## 5. The shape of one memory entry

```markdown
## Bedrooms need an exterior window
- rule: every sleeping room has an operable exterior window; light and ventilation minimums apply
- status: unconfirmed            # unconfirmed | confirmed | wrong
- source: <URL>, read 2026-11-15
- evidence: how we know (a document, a passing report, a measurement)
- applies_to: Los Angeles, R-2 occupancy conversions
```

Status and evidence are required. A wrong note is the main risk: it gets carried into every later run (Anthropic's
example: a false belief about a cave's location sent the agent off the same ledge three times).

## 6. The text we give agents about memory

Tell agents what memory is for, not a procedure. Frontier models handle the rest. Put this in every agent's prompt:

```text
Memory lives in /memories. Read /memories/INDEX.md first, then only the files relevant to this task.
Memory is for what you cannot look up again and will need again: rules you researched, strategies that worked
or failed and why, problems with the data. Do not store numbers or geometry a tool can give you.
Write only inside /memories/<your name>/. Give every entry a status (unconfirmed, confirmed or wrong), a source
and the evidence. Write when something is clearly worth remembering or when asked. Keep files short: edit or
delete an outdated entry rather than adding a new one beside it.
Your context may be reset at any moment. Anything not written to /work/ or /memories/ is lost.
```

The last sentence is the "assume interruption" line from Anthropic's memory tool protocol.

## 7. Context each agent gets

| Agent | Gets in its prompt | Reads on demand | Writes | Returns |
|---|---|---|---|---|
| Orchestrator | Its prompt (section 8), `INDEX.md` | Everything | `/work/<run>/layout.json`, `INDEX.md`, `data/quirks.md` | The final layout and summary |
| Layout | Priorities, the floor id | `floor.json`, `structure.json`, `compliance/la.md`, `layout/lessons.md` | `draft_vN.json`, `layout/` | Five lines and the draft path |
| Compliance | City, draft path | `compliance/la.md`, web search, geometry tool | `compliance_report.md`, `compliance/` | Pass/fail per unit and the report path |
| Cost | Unit list path | `costar.md`, `cost/assumptions.md` | `cost.md`, `cost/` | Units, monthly rent, simple return |

Subagents exchange file paths, not long text. Old tool results are cleared from context once they are large; the
harness already does this (`graph.py`).

## 8. Orchestrator prompt (draft)

```text
You turn one office floor into a rough-draft apartment layout for a developer. The developer needs the overall
idea of what to build, not exact inches.

Priorities, in order:
1. Never place a wall through the building core or a column. Columns are low-confidence guesses; avoid them anyway.
2. Every bedroom touches an exterior window.
3. Every unit is within the allowed walking distance of an exit. Exits are assumed at the core; say so.
4. Maximise rent from the units that fit.

Process: layout drafts, compliance checks against Los Angeles rules, layout fixes failures (at most twice), cost
estimates. Write /work/<run>/layout.json. State every assumption and every rule you could not confirm.
```

## 9. Dreaming (consolidation between runs), later

Anthropic's "dreaming" reviews past sessions offline and rewrites memory: checks notes against the transcripts, merges
duplicates, fixes errors, prunes and keeps the index small. For us, a nightly job (or one manual step before the demo)
can:

1. Check each `unconfirmed` rule against its source and mark it confirmed or wrong.
2. Merge duplicate lessons and delete stale ones.
3. Rewrite `INDEX.md` to stay under 60 lines.

Not needed for the hackathon. The ownership and status rules above are what keep memory usable until then.
